# Complete-build Offline Installation Implementation Plan

Parent review (2026-11-13): this map is approved for the owner-authorized BATCH after commit. Every implementation and acceptance gate remains unverified until its named tests run. No acceptance is delegated.

> **For agentic workers:** Use `superpowers:executing-plans` for the authorized BATCH, with the repository's testbench-before-implementation and review gates. Steps below are checkboxes. This document is a Mode A contract/map only; it does not authorize implementation or change any acceptance status.

**Goal:** After one complete online installation, reopen the same production build offline and use every implemented workspace, including previously unopened CAD, Photo RAW and Python runtimes.

**Architecture:** Generate an exact manifest from the production output. A service worker installs each complete build into an isolated cache generation and publishes it only after every asset passes integrity/header checks. The existing app exposes installation status; updates wait for all app tabs to close and never reload or replace a live document.

**Tech stack:** Existing TypeScript, Vite, native Service Worker/Cache Storage/Web Crypto, node:test and real Chrome/Playwright. No new dependency or server API.

**Spec:** [SYS-010 and related requirements](02-REQUIREMENTS.md), [persistence/offline architecture](03-ARCHITECTURE.md#persistence-offline-and-delivery), [D04/D06 decisions](DECISIONS.md), [consumer continuation](PLAN-2026-11-12.md#consumer-completion-continuation-owner-2026-11-13), and [D06/D08/D21 delivery concepts](MODULE_MAP-MEDIA.md#phase-5--cross-workspace-and-distribution-bricks).

## Global constraints and scope

- The product shall work offline after its first successful load. A load is offline-ready only after the complete build is verified and the current page is controlled by the matching worker; showing the editor alone is not success.
- No account, telemetry, upload, remote runtime, package download during editing, backend processing, or document-serving endpoint. Cache only explicit static build assets. User projects, sources, media, IndexedDB, recovery and Recent remain outside the offline cache.
- Every emitted asset is **strictly below 26,214,400 bytes**; reject equality. At most 20,000 emitted files. Check actual decoded/uncompressed file bytes, including generated worker/manifest outputs.
- Preserve COOP `same-origin`, COEP `require-corp`, CORP `same-origin`, MIME types, and existing Code sandbox/CSP boundaries on network and cached responses. Never add a permissive CORS header or relax Code's network isolation.
- Keep Luna/XP chrome and keyboard access at 1280×720. Installation never takes focus or blocks editing. Cache failure never closes a document or modifies its history.
- No implementation in this pass. S16–S21 below are the next unused shared IDs, all **PLANNED**. They refine the browser/static portions of D06, D08 and D21; D07 and the native M1a launcher/package contracts remain separate, unimplemented gates.
- Each brick has one public factory, at most three public symbols, at most three direct brick collaborators, a sibling testbench and demo, and fewer than 300 implementation lines. Build leaves first; no stubs for later bricks.

## Product and lifecycle contract

### Installation and readiness

1. Register only in production, at stable same-origin `/offline-sw.js`, scope `/`, `updateViaCache: 'none'`. Vite development fixtures do not register a persistent worker.
2. Every build receives one 64-lowercase-hex build ID before bundling. The build plugin injects `<meta name="gsnv-build-id">` into HTML and embeds that same ID/manifest into the bundled worker. Generate a fresh cryptographic ID for a production build; tests supply a fixed ID. Asset hashes verify bytes independently, avoiding a self-referential manifest hash.
3. The worker's manifest is embedded, not fetched from a mutable URL during installation. `/offline-manifest.json` is an inspectable build artifact. Exclude that file, `/offline-sw.js`, and deployment-control `/_headers`/`/_redirects` from precaching; still size/count-gate them. No other output file is silently excluded.
4. Download with concurrency **1**, same-origin only, credentials omitted, redirects forbidden, HTTP cache bypassed. Require status 200, expected MIME essence, required headers, exact byte length and SHA-256. Enforce the declared length while reading, aborting oversized streams. Bounds: 128 MiB precache total, 90 seconds per asset, 10 minutes per installation, no automatic infinite retry. Report these as install errors, not partial readiness.
5. Cache each attempt under a new owned generation name. Write all verified responses plus a completion receipt, then publish one per-build pointer with a single `Cache.put` in a small metadata cache. Only a published, audited complete generation is eligible to serve. Failure deletes that attempt only; the previous complete pointer/cache remains unchanged. Browser termination before publication leaves an ignored candidate; after publication the receipt identifies the complete generation.
6. Use `installEvent.waitUntil()` for the entire operation. A rejected install cannot activate. Audit the published manifest entries and bytes once on worker startup, after a changed generation, and on an explicit readiness check before reporting ready; absent, corrupt or evicted content is `offline.incomplete`, never inferred ready from a stored boolean. Share an in-flight audit and retain its result for that worker/generation. Routine status messages and asset fetches use that result; they must not rehash the full build. Each cache miss immediately revokes readiness; an explicit Check or Retry performs a fresh audit.
7. On the first installation, the active worker may claim existing windows only after every live in-scope window answers a bounded build-ID handshake with the same build. Wait at most 5 seconds; unknown/older tabs leave state `reopen-required`, without forcing a reload. The ordinary single-tab first load must become controlled and ready without a second load. Do not claim windows during an update.

### Serving and updates

- Serve `GET /` and `GET /index.html` navigation from the current complete build's `/index.html`; query strings on those two navigation paths do not change the document. Serve exact manifest asset URLs from that build. Do not return HTML for missing JS/WASM, cache POSTs, intercept blob/data URLs, fetch a URL supplied in a message, or store non-manifest requests.
- Match a `Request`, not merely its URL. For cached manifest assets, preserve full-response semantics and implement a single byte range with exact `206`, `Content-Range`, `Content-Length` and `Accept-Ranges`; return `416` with the complete length for an unsatisfiable single range. An `If-Range` mismatch or unsupported/multiple range may return the complete `200` response, never a fabricated partial response. These fallback semantics follow [HTTP range handling](https://www.rfc-editor.org/rfc/rfc9110.html#section-14.2). Preserve the original request and its headers on network fall-through. User file/blob/media URLs never enter this static-asset path.
- If the published generation becomes incomplete, revoke readiness and stop serving it as a complete offline build. Online network fall-through may keep the app usable; failed offline navigation receives a small readable error response with the isolation headers. Retry rebuilds a separate generation and only replaces the pointer when complete. No partial candidate is ever served.
- A successful update stays **waiting** while any old app tab is open. Never call `skipWaiting()`, automatically reload, clear recovery, or discard dirty work. UI: **“Update ready. Save your work, close all gsnv-paint tabs, and reopen.”** A page refresh is not advertised as sufficient.
- A failed update reports its error while the old active build remains **Ready offline**. The failure must not replace that old readiness state. Every worker uses its own embedded manifest, so an old tab never selects a candidate build's cache.
- After natural activation with no old controlled clients, retain the current build and the most recently published other complete build, using receipt time and deterministic generation-name tie-breaking. Remove only older owned generations and abandoned candidates. Cleanup failure is diagnostic and must not fail activation or invalidate a complete build. Never clear all origin storage or any other application's caches. Candidate quota failure must not delete a usable build to make space.
- No immediate-update control in this increment. This intentionally avoids a multi-tab unsaved-work handshake and preserves the existing shell's beforeunload/confirmed-backup protection. Manual close still runs the shell's current warning/flush behavior.

### Status and failure contract

`OfflineState = { phase: 'unavailable'|'checking'|'installing'|'ready'|'reopen-required'|'error'; pageBuild: string; readyBuild?: string; completedBytes: number; totalBytes: number; update: 'none'|'checking'|'installing'|'ready'|'error'; error?: {code: string; message: string} }`.

The compact status control says **“Preparing offline…”**, **“Ready offline”**, **“Reopen to enable offline”**, or **“Offline unavailable”**. Its keyboard-accessible details show progress, an error/recovery instruction and **Retry offline setup** / **Check for updates** as applicable. Use text nodes and a polite status announcement; throttle progress announcements to once per second. Escape closes details and returns focus. Storage denial/quota, missing/insecure service-worker support, timeout, HTTP/MIME/header failure, digest mismatch, version mismatch and eviction have distinct actionable messages. Connectivity alone never determines readiness.

Error codes: `offline.unsupported`, `offline.network`, `offline.integrity`, `offline.headers`, `offline.limit`, `offline.quota`, `offline.storage`, `offline.incomplete`, `offline.version`, `offline.cancelled`. Retry uses only the embedded manifest, never user input URLs. Browser storage can be cleared or evicted externally; the product detects this when it can run and requires reconnection/reinstallation, rather than promising permanent storage.

## Boundary types and modules

`OfflineAsset = { url: string; bytes: number; sha256: string; mime: string }`. URLs are unique canonical root-relative static paths without query/hash, traversal, backslash, NUL or encoded separators; `/index.html` is required. `OfflineManifest = { schema: 1; build: string; assets: readonly OfflineAsset[] }`. Byte counts are nonnegative safe integers; SHA-256/build IDs are 64 lowercase hex characters; assets are sorted by URL and total at most 128 MiB.

Cache namespace: `gsnv-paint:offline:v1:meta` plus `gsnv-paint:offline:v1:build:<build>:<attempt>`. Reserved internal metadata request paths are not manifest assets and are never served. `OfflineReceipt = { schema: 1; build: string; generation: string; files: number; bytes: number; publishedAt: number; complete: true }`; `publishedAt` is a finite nonnegative clock value used only for cleanup ordering, never integrity/readiness.

## Build and application assembly

The S17 Vite plugin injects build identity before the normal app bundle. Its post-build stage inventories that finished output and uses the **existing Vite API with `configFile:false`** to bundle the wiring-only `src/app/offline-entry.ts` as the one `/offline-sw.js`. ## Recommendation and bounded decisions

Approve this as the S16–S21 shared offline increment, then implement in order **S16 → S18 → S19 → S17 → S20 → S21 → assembly**. Each brick has an independent real demo before its consumers advance. Keep updates deferred until all tabs close; an immediate-update button would require a separate reviewed cross-tab save/backup contract. Keep the current source launcher for this increment; do not claim the planned native M1a distribution is finished.

The proposed 128 MiB cache budget and sequential download bound cover the observed approximately 40 MiB runtime payload without assuming browser quota. Their actual install duration, peak memory and fresh-process offline behavior remain UNTESTED. A browser cache is not a substitute for saving user files.

Platform references checked 2026-11-13: the browser waits to activate a replacement worker until old controlled clients are gone, which supports the deferred update policy ([service-worker lifecycle](https://web.dev/articles/service-worker-lifecycle)); registration uses an explicit HTTP-cache policy for worker updates ([Chrome update behavior](https://developer.chrome.com/blog/fresher-sw)); individual cache batch operations provide the publication boundary, while multiple cache writes are not one transaction ([Service Worker cache specification](https://w3c.github.io/ServiceWorker/#cache-batch-cache-operations)); the current Pages limit remains 25 MiB per file and 20,000 files on Free ([Cloudflare limits](https://developers.cloudflare.com/pages/platform/limits/)).

Self-review: required first-load completeness, lazy assets, same-build cold restart, safe failed update, dirty multi-tab update, static-only/privacy, header preservation and size gates each have a named owner and test above. No application modules, tests, configuration or dependencies were created for this map. Parent review/commit precedes BATCH implementation.
